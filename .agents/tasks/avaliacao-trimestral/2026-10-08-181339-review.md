# Quarterly evaluation cycles (periods per quarter) for PDI Cloud

Adds per-quarter evaluation to a static (no-build, IIFE globals) app so leaders can track collaborator evolution every three months. The data model moves from flat `member.scores`/`member.plan` to `member.periods['YYYY-Qn'] = { scores, plan }`, with a lazy, non-destructive, idempotent migration living entirely in the Store layer (both LocalStore and Firebase). The UI gains a global quarter selector on Avaliação / Nine Box / Plano, period-aware Model calculations, and a new "Evolução" line chart of the three pillar averages per quarter. The firebase config and firestore.rules are untouched; the dark theme is reused via existing CSS variables.

Watch for: nothing blocking — the quarter key format, current-quarter derivation, migration round-trip, and period-aware calcs all check out against the plan and the FEAT acceptance criteria (confirmed by reading store.js/model.js/app.js). The one gap is purely verification: no Node/headless browser exists in this environment, so the `?selftest` asserts and the in-browser click-through were validated by code inspection rather than executed (possible).

**Verdict**: APPROVED

## High-level view

The period key is `"YYYY-Qn"` on the civil calendar, derived as `year + '-Q' + (Math.floor(month/3)+1)` from a 0-indexed month, so Jan-Mar=Q1 through Oct-Dec=Q4. Quarter arithmetic for the prev/next selector converts the key to an absolute quarter index (`y*4 + (q-1)`), shifts, and rebuilds, handling year rollover in both directions.

Migration is confined to the Store. `migrateOnRead` adds `periods[currentQuarter] = { scores, plan }` only when `.periods` is absent, mutates in place, keeps the legacy root fields, and is a no-op when `.periods` already exists. `prepareForWrite` strips the root `scores`/`plan` on save — via `FieldValue.delete()` in Firebase mode and plain omission in local mode — so the legacy fields can't resurrect under `{ merge: true }`. Both helpers are wired into `list` and `save` on both store implementations.

Model calcs take an explicit `periodKey` and resolve scores through a single `periodScores` accessor. Once a member has `.periods`, an unknown/empty quarter returns `{}` rather than leaking the legacy root scores, so empty quarters read as genuinely empty; the legacy root fallback only applies to never-migrated objects. The radar team-average overlay and the Nine Box both receive the same `selectedPeriod`, satisfying the "same quarter for both" requirement.

The quarter selector is a single JS-rendered bar reused across the four views; `selectedPeriod` is the one source of truth and switching re-renders only the active view. The Evolução chart sorts the member's existing period keys ascending and plots one line per pillar; collaborators see only their own data (select hidden). Collaborator read-only is preserved because `canEdit()` gating is unchanged.

### Period key format and quarter arithmetic

`periodKeyFor` reads `d.getMonth()` (0-indexed) and computes `Math.floor(month/3)+1`, giving Q1 for Jan-Mar through Q4 for Oct-Dec, formatted as `year + '-Q' + n`. This matches the `/^\d{4}-Q[1-4]$/` acceptance criterion and the plan's fixed-calendar rationale.

`shiftPeriod` splits on `-Q`, forms the absolute index `y*4 + (q-1) + delta`, then rebuilds `ny = Math.floor(idx/4)`, `nq = (idx%4)+1`. Checked at the boundaries: `2025-Q4 +1 → 2026-Q1` and `2025-Q1 -1 → 2024-Q4`, both correct, so the prev/next buttons roll the year over cleanly.

### Lazy, non-destructive, idempotent migration

```js
function migrateOnRead(member) {
  if (!member) return member;
  if (!member.periods) {
    member.periods = {};
    member.periods[currentPeriodKey()] = { scores: member.scores || {}, plan: member.plan || [] };
  }
  return member;
}
```

A pure read never drops data: legacy root `scores`/`plan` stay in memory and are only removed by `prepareForWrite` on an actual save. The `if (!member.periods)` guard makes a second read a no-op, so reading a member twice yields the same structure. `prepareForWrite` uses `firebase.firestore.FieldValue.delete()` in Firebase mode (necessary because `set(..., { merge: true })` would otherwise leave stale root fields) and `delete payload.scores/plan` in local mode. Both `LocalStore` and the Firebase store map reads through `migrateOnRead` (leader snapshot and single-collaborator-doc branch both covered) and route writes through `prepareForWrite`.

### Period-aware Model and the empty-quarter boundary

```js
function periodScores(member, periodKey) {
  if (member && member.periods) {
    const p = periodKey && member.periods[periodKey];
    return (p && p.scores) || {};
  }
  return (member && member.scores) || {};
}
```

The ordering matters: once `.periods` exists, an unknown quarter returns `{}` and does not fall back to the legacy root scores, so a quarter the person was never evaluated in reads as empty instead of inheriting old numbers. The legacy fallback is reachable only for objects that were never migrated (synthetic/old call sites with `periodKey` undefined), preserving retrocompat. All calc entry points (`pillarAverage`, `memberScoresByCompetency`, `teamAverageByCompetency`, `weightedAxis`, `performanceScore`, `potentialScore`, `nineBoxCell`, `nineBoxLabel`) thread `periodKey` through to this accessor.

### Quarter selector driving reads and writes; same quarter for radar and Nine Box

`selectedPeriod` (default `Store.currentPeriodKey()`) is the single source of truth. `renderQuarterBar` is rendered at the top of all four period-aware views; prev/next call `setSelectedPeriod`, which updates state and re-renders only the active view. `memberPeriod(member, create)` returns an ephemeral empty `{ scores:{}, plan:[] }` on read when the quarter is absent (no mutation) and materializes `member.periods[selectedPeriod]` on write, so switching to an empty quarter shows nothing and switching back shows the saved data. `setScore` writes into the materialized period, calls `Store.save` (which strips the root fields), and re-syncs the in-memory `members[]` entry. In the radar, both `memberScoresByCompetency` and `teamAverageByCompetency` receive `selectedPeriod`; `renderNineBox`, its legend, and the guide counts all use `selectedPeriod` — the team-average overlay and the Nine Box therefore always reflect the same quarter.

### Evolução line chart and collaborator scoping

`renderEvolution` builds `periodKeys = Object.keys(member.periods||{}).sort()` ascending (falling back to the current quarter when empty so the chart isn't blank) and emits one `line` dataset per `Model.PILLARS` pillar, with `data = periodKeys.map(k => Model.pillarAverage(member, pillar, k))`, pillar `color`, and a `0..Model.SCALE_MAX` y-axis. The prior `evolutionChart` is destroyed before redraw. The member select defaults to `members[0]`, re-renders on change, and is hidden for a collaborator (`!canEdit() && members.length <= 1`), who only ever receives their own doc from `Store.list()`. The axis/legend colors reuse the dark palette already used by the radar and Nine Box.

### Self-tests

`runSelfTests` runs only when `location.search.includes('selftest')` and operates on synthetic objects, so real data is never touched. It exercises the real `Store.migrateOnRead` (now exposed) to confirm a legacy member gains `periods[currentQuarter]` with its scores/plan intact, that an already-migrated member is left unchanged with no root scores, and that `Model.pillarAverage(migrated, PILLARS[0], current) === (4+2)/6` — the two set HardSkill competencies (4 and 2) summed over the pillar's six competencies. The arithmetic is correct.

### Scope and regression surface

The diff touches only `index.html`, `styles.css`, `js/app.js`, `js/model.js`, `js/store.js` (plus the task FEAT json files). `firebase-config.js` and `firestore.rules` are not in the diff. The brand `<h1>` reads "PDI Cloud". Login/roles, the Usuários view (including the delete-member button at `#btn-delete-member`), and the Tutorial markup are unchanged. New members are still created with a root `scores:{}`, which the first save migrates and strips — consistent with the non-destructive contract.
